# 拾序 Agent 架构设计

> 状态：单 Agent、人机确认、同账号多对话与不做跨对话长期记忆已确认。阶段 4 模型选用 MiMo `mimo-v2.6-flash`，Tool 及运行限额见开发计划与 API 契约。

语音入口按 [ADR 0004](./adr-0004-local-voice.md)：前端本地转写，后端先校准与核验初步文字。校准不是 Agent turn；用户主动发送前不创建消息或 run。

## 1. 设计目标

Agent 帮用户管理事务：理解自然语言、查询事务、提出创建/修改/完成/删除提案，并在信息不足时追问。首期采用一个 Agent、一个 LLM、多个受限业务 Tool。Application 用例编排 LLM 与 Tool；Agent 不直接访问数据库，也不能自行确认任务变更。

经典 5×5 舒尔特表由前端独立提供；Agent 不处理训练或眼动数据。对话记录是用户可见的持久会话数据，不是跨对话长期记忆。用户显式保存的任务和必要偏好属于业务数据，可由另一个对话按需查询；不自动抽取习惯、人格或跨会话画像。

## 2. 身份、数据与会话边界

- 用户可公开自助注册用户名与密码并登录。后端验证后设置安全会话 Cookie；每个业务请求从会话查得内部 user_id。首期不提供自助密码找回。
- 前端不在请求中指定 user_id，也不保存会话凭证到 localStorage。Agent Tool schema 不含 user_id。
- 用户数据包括任务、必要偏好、对话、消息、提案和 run；全部归属已认证账号。
- 任务是当前产品事实，服务端数据库为权威；新账号初始为空，不导入旧 localStorage 样例。
- 用户可创建多个对话、查看并继续旧对话；对话保留到用户手动删除。
- 新对话不装载旧对话历史或摘要。当前对话接近上下文限制时，可以保存当前对话摘要帮助续接；摘要永远不能替代任务数据库的当前事实。
- 删除对话清理其消息、摘要、未完成提案和关联运行数据，不删除任务。删除任务独立执行。
- 同一个账号在不同设备间共享任务、偏好和对话；每台设备可持有各自独立的登录会话。

## 3. 运行与持久化

    Web 前端
      → HTTPS API：Cookie 验证
      → Application 读取 conversation 和 user_id
      → 用户主动发送校准/编辑后的文字，创建并持久化用户消息、agent_run
      → Worker 取得待处理 run
      → 单 Agent / MiMo `mimo-v2.6-flash`
      → 受限业务 Tool → Application Use Cases → PostgreSQL
      → 保存助手回复、提案、run 状态与有序事件
      → SSE 推送给前端；断线后按 run 状态/事件重放

创建消息、开始 run、订阅 SSE 为两阶段流程。PostgreSQL 保存 run 和用于恢复的事件记录；内存事件队列可以加速当前连接，但不作为唯一事件历史。阶段 4 冻结每 run 最多 16 次模型请求、16 次只读 Tool 调用、180 秒和 64K/8K 输入/输出 tokens。worker 每次运行使用独立 DB Session，不在并发任务之间共享；完整限流值见开发计划。

## 4. Agent Tool 职责

### 只读查询工具

- search_tasks：按关键词、日期范围、重要度、紧急度、状态和分类查找当前账号事务；限制分页、返回数量与字段。
- get_task：读取当前账号单条事务的最新状态和 version。

工具调用的账号范围由 Application 从认证上下文注入。Tool 参数不能包含 user_id。每次查询都验证任务属于当前账号，不能依据模型给出的 ID 直接信任归属。

### 提案生成与任务写入

Agent 可以提出任务操作，但不能直接提交：

- create_task proposal
- update_task proposal
- complete_task proposal
- delete_task proposal

提案包含稳定 proposal_id、会话 ID、操作类型、目标任务、expected_version、允许字段的 patch、面向用户的变更摘要、状态和过期时间。模型生成的 patch 经 API Schema、Domain 和授权校验后仍只是待确认提案。

用户确认提案时，Application 再次检查账号归属、状态、有效期、任务版本与幂等键，然后在一个明确的数据库事务中执行。失败或冲突不部分写入；版本变化时基于最新任务重新生成提案。

页面完成勾选也必须生成待确认意图；用户确认后由统一确认用例写入并返回真实回执。永久删除没有软删除撤销入口。

## 5. 人机交互

| 用户行为 | 系统行为 |
|---|---|
| 查询任务 | 直接执行查询并展示真实结果，无需额外确认 |
| 信息不充分 | 先追问或列候选，不产生写入 |
| 口头/文本请求创建、修改、完成或删除 | 返回提案卡片，展示任务和变更；等待用户点击确认 |
| 用户点完成勾选 | 生成待确认意图，用户确认后执行状态变更 |
| 提案过期、冲突或对象无权限 | 不执行；返回明确状态，不透露其他账号对象存在与否 |
| 用户删除对话 | 取消/终止未完成运行，清理该对话数据；任务独立保留 |
| 模型或工具失败 | 保留用户消息，说明失败并允许重试；不宣称任务已更新 |

确认使用明确的 UI 控件，不要求用户再发送一个文字“确认”。Agent 状态消息仅解释处理阶段，不包含内部推理文本。

## 6. 上下文装配

Application 为每个 run 提供以下最少上下文：

- 系统规则和允许的 Tool/schema。
- 当前已认证账号的 user_id（仅内部授权上下文，不传给模型）。
- 当前 conversation 的必要消息历史与当前用户消息。
- 当前时间与用户明确设置的时区。
- 若输入来自语音，校准后的文字仍作为不可信请求处理：核验日期/时间、内容完整性、任务意图、目标任务归属和业务规则；不能因前端转写或校准标记跳过授权。
- 需要时通过只读 Tool 得到的相关任务数据。
- 若会话历史过长，仅压缩当前 conversation 的早期内容，保留用户纠正、待解决问题和提案引用。

不向模型发送整个任务表；不将其他对话消息或摘要并入当前上下文；不把模型内部推理保存到消息。用户消息和可见助手回复作为对话历史保存，Agent run/工具过程事件只返回安全的用户可见状态。

## 7. LLM 与 Tool 防护

- 优先使用所选供应商支持的结构化输出与严格 Tool schema，使用固定 Tool 名称、明确参数描述、枚举和禁止额外字段。
- Schema 限制不等于业务授权；应用对每个调用重新做类型、长度、对象归属、字段白名单、速率、轮次和权限检查。
- Tool 只调用 Application Use Case，不调用 ORM/SQL。
- Tool 返回仅含继续当前任务所需的数据，限制敏感内容、记录数和 token。
- Agent 只能访问后端显式注册的 Tool，不允许任意 URL、Shell、SQL、反射调用或模型自创 Tool。
- 低置信度、用户主动重试或后端无法判断时才可由前端提出可选音频二次转写；该流程不自动发送消息、启动 run 或确认任务提案。
- LLM API Key 仅位于后端环境变量或 Secret；提示词和日志不含密钥。

OpenAI Function Calling 官方建议使用清晰可预测的工具描述、strict schema，并要求应用验证工具参数和权限。见后端架构设计的官方链接。

## 8. 失败与恢复

- run 创建后立即持久化用户消息和 run 记录；如果模型不可用，用户仍能看到自己的消息和明确失败状态。
- SSE 断线不代表 run 取消；前端通过 run status 和事件序号恢复。
- 消息提交重试使用 client_message_id / 幂等键，防止重复创建消息和 run。
- 提案确认使用 idempotency key；不能因浏览器重试重复修改任务。
- Worker 在中止/重启后必须将领取的 run 收敛到明确状态，或安全恢复执行；未知提交结果先查数据库，不盲目重放。
- Tool 轮次、总时间、输入与输出 token 有硬上限。超过预算时保存部分用户可见状态并终止 run。
- 关联日志只记录 request_id、user_id 的内部关联 ID、conversation_id、run_id、Tool 名称、状态与耗时；不记录密码、session token 或对话正文。

## 9. 不在首期范围

- 多 Agent、跨对话长期记忆、自动用户画像或隐式偏好学习。
- Agent 直接写任务，或仅因模型发起 function call 就视作用户授权。
- 训练 API、眼动、提醒、邮件/短信通知、文件库和向量检索。
- 用 LangGraph、Redis 或独立微服务处理当前尚未证明需要的编排。

## 10. 阶段 5 任务提案接入

阶段 5 允许 Agent 通过受限的 `propose_create_task`、`propose_update_task`、
`propose_complete_task` 和 `propose_delete_task` Tool 保存结构化待确认提案。
这些 Tool 只调用 Application 的 proposal 用例，不直接修改任务；模型调用成功后，
用户仍必须通过现有 proposal confirm API 明确确认，任务写入才会发生。Tool 请求 ID
由服务端根据 run 与 tool call 生成，避免重复执行同一调用造成重复提案。

阶段 5 不扩展 task reports、check-ins、语音或任务重要度字段；这些仍需单独冻结入口
协议后实施。

## 11. 语音输入边界

语音首选链路为“前端本地转写 → 后端校准和业务核验”。前端负责麦克风录音与本地语音转文字，只向后端提交初步文字；后端必须校准文本格式、标准化日期/时间、检查内容完整性、识别任务意图并核验业务规则，不能把前端转写结果直接当作事实或授权。

默认不上传原始音频。只有前端低置信度、用户主动重试或后端无法判断时，才允许进入可选的音频上传/二次转写流程。用户编辑并明确发送前，不创建对话消息或 Agent Run；涉及任务创建、修改、完成或删除时，校准结果只能转换为待确认提案，不能直接写任务。

阶段 6 参数见 [ADR 0005](./adr-0005-speech-stage-6.md)。后端校准接口不保存草稿；无法确定具体任务或日期时返回澄清，不擅自生成已确认的业务事实。前端本地模型的真实设备性能仍待联调。
